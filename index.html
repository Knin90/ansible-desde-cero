¿Qué es Ansible?

Ansible es una herramienta de automatización de TI de código abierto creada por Michael DeHaan en 2012 y adquirida por Red Hat en 2015. Permite automatizar el aprovisionamiento de servidores, la gestión de configuraciones, el despliegue de aplicaciones y la orquestación de flujos de trabajo complejos en infraestructuras de cualquier tamaño.

A diferencia de otras herramientas similares, Ansible no requiere instalar ningún agente en los servidores gestionados. Se comunica con ellos mediante SSH (en Linux/macOS) o WinRM (en Windows), aprovechando la infraestructura de red ya existente.

Filosofía de Ansible

  • Sin agentes (agentless): no se instala ningún software adicional en los nodos gestionados. Solo se necesita SSH y Python en el servidor remoto.
  • YAML declarativo: los playbooks describen el estado deseado del sistema, no los pasos concretos para llegar a él. El lenguaje es legible por humanos.
  • Idempotente: ejecutar el mismo playbook varias veces produce siempre el mismo resultado. Si el sistema ya está en el estado deseado, Ansible no realiza ningún cambio.
  • Basado en push: el nodo de control envía las instrucciones a los nodos gestionados, sin necesidad de que éstos las soliciten.

Casos de uso habituales

  • Aprovisionamiento de servidores: instalación del sistema operativo, paquetes y configuración inicial.
  • Gestión de configuraciones: mantener ficheros de configuración consistentes en toda la flota de servidores.
  • Despliegue de aplicaciones: actualizar código, reiniciar servicios y gestionar migraciones de base de datos.
  • Orquestación multi-capa: coordinar el despliegue de sistemas con bases de datos, backends, balanceadores y frontends.
  • Automatización de seguridad: aplicar parches, endurecer configuraciones y auditar el cumplimiento de políticas.

¿Cómo funciona Ansible?

Ansible opera desde un nodo de control (tu máquina de trabajo o un servidor de CI/CD). Este nodo de control lee el inventario para saber qué máquinas gestionar y el playbook para saber qué tareas ejecutar. La comunicación con los nodos gestionados se realiza íntegramente mediante SSH: Ansible sube módulos Python temporales al nodo remoto, los ejecuta y los elimina. No queda ningún proceso residente en los servidores.

El flujo completo es: leer el playbook → leer el inventario → conectar por SSH a cada host → subir y ejecutar los módulos Python necesarios → recoger el resultado → informar del estado (changed / ok / failed). Todo esto ocurre de forma paralela para todos los hosts del grupo, con un número de conexiones simultáneas configurable mediante el parámetro forks.

Estructura del proyecto

Un proyecto Ansible bien organizado separa el inventario, los playbooks y los roles en directorios distintos. La estructura siguiente es la convención habitual y la que reconoce automáticamente Ansible al buscar roles y variables:

  • 📁 mi-proyecto-ansible/
    • 📁 inventory/
      • hosts.ini
      • 📁 group_vars/
        • all.yml
    • 📁 playbooks/
      • sitio.yml
    • 📁 roles/
      • 📁 servidor_web/
        • 📁 tasks/
          • main.yml
        • 📁 handlers/
          • main.yml
        • 📁 templates/
          • nginx.conf.j2
        • 📁 files/
          • index.html
        • 📁 vars/
          • main.yml
        • 📁 defaults/
          • main.yml
        • 📁 meta/
          • main.yml
    • ansible.cfg
    • README.md

Elementos estructurales

Cada directorio y fichero del proyecto Ansible cumple una función concreta. Despliega cada elemento para ver su descripción y un ejemplo real en YAML.

📋 Inventory — inventario de hosts

El inventario define qué máquinas gestiona Ansible y cómo se agrupan. Puede ser un fichero estático en formato INI o YAML, o bien un inventario dinámico que consulta una API (AWS, GCP, Azure, Terraform…). Los grupos permiten aplicar tareas y variables a conjuntos de hosts de forma selectiva. 

# inventory/hosts.ini
[servidores_web]
web1.ejemplo.com
web2.ejemplo.com ansible_user=admin

[bases_de_datos]
db1.ejemplo.com

[all:vars]
# Variable aplicada a todos los hosts
ansible_python_interpreter=/usr/bin/python3

Consejo: Usa group_vars/ para definir variables por grupo en lugar de escribirlas directamente en el fichero hosts.ini. Así el inventario queda limpio y las variables son fáciles de sobreescribir por entorno.

📄 Playbooks — orquestación de tareas

Un playbook es un fichero YAML que contiene uno o más plays. Cada play asocia un conjunto de hosts con una lista de tareas y define opciones como el usuario remoto, la escalada de privilegios o las variables del play. Los playbooks son el punto de entrada principal para ejecutar Ansible (ansible-playbook sitio.yml). 

# playbooks/sitio.yml
---
- name: Configurar servidores web
  hosts: servidores_web
  become: true          # Escalar a root con sudo
  vars:
    puerto_http: 80
  roles:
    - servidor_web      # Aplica el role completo

- name: Configurar base de datos
  hosts: bases_de_datos
  become: true
  roles:
    - base_de_datos

Consejo: Mantén los playbooks delgados: que solo referencien roles y definan variables de alto nivel. La lógica real vive dentro de los roles, lo que facilita la reutilización.

📦 Roles — unidad de reutilización

Un role encapsula un conjunto completo de tareas, handlers, variables, templates y ficheros relacionados con una funcionalidad concreta (por ejemplo, instalar y configurar nginx). Los roles son la unidad de reutilización fundamental de Ansible: se comparten en Ansible Galaxy y se instalan con ansible-galaxy install. 

# roles/servidor_web/meta/main.yml
---
galaxy_info:
  author: tu_usuario
  description: Instala y configura nginx con soporte HTTPS
  license: MIT
  min_ansible_version: "2.14"
  platforms:
    - name: Ubuntu
      versions: ["22.04", "24.04"]
    - name: EL          # Enterprise Linux (RHEL, Rocky, Alma)
      versions: ["9"]

dependencies:
  - role: geerlingguy.firewall   # Role de Galaxy del que dependemos
    vars:
      firewall_allowed_tcp_ports: ["80", "443"]

Consejo: Declara siempre las dependencias en meta/main.yml en lugar de importarlas manualmente en el playbook. Así Ansible las resuelve automáticamente y el role es verdaderamente autocontenido.

✅ Tasks — lista de acciones

Las tasks son la unidad de trabajo elemental en Ansible. Cada task invoca un módulo (package, service, template, copy, file, command…) con los argumentos necesarios para llevar el sistema al estado deseado. Se ejecutan en orden, de arriba a abajo, en cada host del grupo. 

# roles/servidor_web/tasks/main.yml
---
- name: Instalar nginx
  ansible.builtin.package:
    name: nginx
    state: present        # Instalar si no está presente (idempotente)

- name: Copiar configuración de nginx
  ansible.builtin.template:
    src: nginx.conf.j2    # Fuente en templates/ del role
    dest: /etc/nginx/nginx.conf
    owner: root
    group: root
    mode: "0644"
  notify: Reiniciar nginx # Dispara el handler si hay cambios

- name: Iniciar y habilitar nginx
  ansible.builtin.service:
    name: nginx
    state: started
    enabled: true

Consejo: Usa siempre el nombre completamente calificado del módulo (FQCN), por ejemplo ansible.builtin.package en lugar de package, para evitar ambigüedades cuando coexisten múltiples colecciones instaladas.

🔔 Handlers — acciones condicionales

Los handlers son tareas especiales que solo se ejecutan cuando son notificadas por otra tarea mediante notify. Se ejecutan una sola vez al final del play, independientemente de cuántas tareas los hayan notificado. Son ideales para reiniciar servicios solo cuando la configuración ha cambiado de verdad. 

# roles/servidor_web/handlers/main.yml
---
- name: Reiniciar nginx
  ansible.builtin.service:
    name: nginx
    state: restarted      # Reinicio completo del servicio

- name: Recargar nginx
  ansible.builtin.service:
    name: nginx
    state: reloaded       # Recarga de configuración sin cortar conexiones

Consejo: Prefiere reloaded a restarted para nginx y Apache: recarga la configuración sin interrumpir las conexiones activas. Usa restarted solo cuando sea estrictamente necesario (cambio de binario, certificados, etc.).

🔧 Vars — variables del role

El directorio vars/ contiene variables con alta prioridad en la jerarquía de variables de Ansible. Son difíciles de sobreescribir desde el playbook o el inventario, por lo que se usan para valores que el role considera fijos o internos: puertos, rutas de instalación, nombres de paquetes según la distribución, etc. 

# roles/servidor_web/vars/main.yml
---
# Variables internas del role — alta prioridad
puerto_http: 80
puerto_https: 443
nombre_sitio: mi-aplicacion
ruta_config_nginx: /etc/nginx/nginx.conf
paquetes_nginx:
  - nginx
  - nginx-common

Consejo: Si quieres que el usuario del role pueda personalizar fácilmente un valor (como el nombre del sitio o el puerto), ponlo en defaults/ en su lugar. Reserva vars/ para constantes internas que no deberían cambiarse desde fuera.

⚙️ Defaults — valores por defecto

El directorio defaults/ define las variables del role con la prioridad más baja de toda la jerarquía de Ansible. Esto significa que cualquier variable definida en el inventario, en el playbook o en la línea de comandos sobreescribirá automáticamente los defaults. Son la interfaz pública del role: los parámetros que el usuario puede (y debe) personalizar. 

# roles/servidor_web/defaults/main.yml
---
# Valores por defecto — el usuario puede sobreescribir cualquiera de estos
puerto_http: 80
nombre_sitio: mi-sitio
habilitar_https: false
directorio_web: /var/www/html
usuario_nginx: www-data
trabajadores_nginx: auto    # Número de worker processes

Consejo: Documenta todos los defaults con comentarios explicativos. Son la documentación viva de la interfaz del role. Un role bien documentado en defaults/main.yml no necesita un README extenso para entender cómo configurarlo.

📝 Templates — ficheros Jinja2

Los templates son ficheros de texto con extensión .j2 que usan la sintaxis de Jinja2 para insertar variables, aplicar filtros y usar estructuras de control (if, for). Ansible procesa el template en el nodo de control, sustituyendo todas las expresiones, y copia el fichero resultante al servidor remoto mediante el módulo ansible.builtin.template. 

# roles/servidor_web/templates/nginx.conf.j2
# Configuración de nginx generada por Ansible — no editar manualmente
user {{ usuario_nginx }};
worker_processes {{ trabajadores_nginx }};

events {
    worker_connections 1024;
}

http {
    server {
        listen {{ puerto_http }};
        server_name {{ nombre_sitio }};
        root {{ directorio_web }};

        {% if habilitar_https %}
        # Redirigir HTTP a HTTPS
        return 301 https://$host$request_uri;
        {% endif %}
    }
}

Consejo: Añade siempre un comentario al inicio del template indicando que es generado por Ansible y no debe editarse manualmente. Así evitas que alguien modifique el fichero en el servidor y pierda los cambios en el siguiente deploy.

📂 Files — ficheros estáticos

El directorio files/ contiene ficheros estáticos que se copian al servidor remoto sin ningún procesamiento. Se usa para binarios, certificados, scripts o cualquier fichero que no necesite interpolación de variables. El módulo que los copia es ansible.builtin.copy, que detecta automáticamente si el fichero ya está actualizado y omite la copia si no hay cambios (idempotencia). 

# En tasks/main.yml — copiar fichero estático
- name: Copiar página de error 404 personalizada
  ansible.builtin.copy:
    src: 404.html         # Fichero en roles/servidor_web/files/404.html
    dest: /var/www/html/404.html
    owner: "{{ usuario_nginx }}"
    group: "{{ usuario_nginx }}"
    mode: "0644"

- name: Copiar script de health check
  ansible.builtin.copy:
    src: healthcheck.sh
    dest: /usr/local/bin/healthcheck.sh
    mode: "0755"          # Ejecutable

Consejo: Si el fichero necesita variables, usa templates/ con extensión .j2 en lugar de files/. La distinción es simple: files/ = copia literal, templates/ = copia con sustitución de variables Jinja2.
